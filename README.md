# limstack

Markdown으로 쓴 한글 기술 문서를 주제별로 모아 읽는 개인 정적 사이트야. 이 저장소에는 빌더와 설계를 두고, 글과 이미지는 외부 문서 폴더에서 읽어. 현재 구현 범위와 진행 상황은 [설계 문서](docs/README.md)와 [세션 인수인계](docs/세션-인수인계.md)에서 확인해.

## PR 하나의 크기

PR 하나는 리뷰어가 **무엇이 바뀌었고 어떻게 확인하는지** 한 문장으로 설명할 수 있는 단위로 만들어. 예를 들어 ‘공개 빌드에서 초안을 제외한다’는 변경에는 공개 글이 남고 초안이 빠지는 검증까지 함께 담아. [작은 변경을 리뷰하는 원칙](https://google.github.io/eng-practices/review/developer/small-cls.html)

- 이 프로젝트의 목표는 **100줄 안팎, 상한은 200줄**이야. 사람이나 AI가 작성한 코드·테스트·설정·문서의 **추가 줄과 삭제 줄을 합산**해. 30줄을 지우고 20줄을 쓰면 50줄이야.
- PR을 열기 전에 작업 브랜치에서 `git diff --numstat origin/main...HEAD`로 커밋한 변경을 확인해. `package-lock.json`처럼 도구가 생성한 파일은 별도로 세고, PR 본문에 파일명과 줄 수, 생성 이유를 적어.
- 200줄을 넘길 것으로 보이면 구현 전에 동작 단위로 나눠. 200줄 이하여도 서로 다른 결정을 검토해야 하면 PR을 분리해. 각 PR은 관련 검증을 포함하고 단독으로 병합할 수 있어야 해.

## 작업을 나누고 병렬로 진행하기

작업 하나에 **브랜치 하나, worktree 하나, PR 하나**를 사용해. 시작할 때 각 PR의 완료 조건과 먼저 병합해야 할 변경을 적어. 같은 파일이나 아직 정해지지 않은 데이터 형식에 의존하면 공통 변경부터 병합해.

예를 들어 문서 데이터 형식과 상세 페이지의 기본 구조가 `main`에 들어간 뒤에는 아래 두 작업을 병렬로 진행할 수 있어. 저장소 루트에서 실행하면 두 브랜치가 같은 커밋에서 출발하고 작업 폴더는 각각 생겨.

```sh
git fetch origin
git worktree add --no-track -b feat/stack-list ../limstack-stack-list origin/main
git worktree add --no-track -b feat/doc-toc ../limstack-doc-toc origin/main
```

| PR | 리뷰어가 확인할 동작 |
| --- | --- |
| stack별 글 목록을 날짜순으로 표시 | 날짜가 다른 두 글에서 최신 글이 먼저 보인다. |
| 문서 상세에 접힌 목차 추가 | 키보드로 목차를 열 수 있고 소제목이 없는 글에는 목차가 생기지 않는다. |

각 폴더에서 변경을 검증하고 커밋한 뒤 `git push -u origin HEAD`로 해당 브랜치를 올려. GitHub에서는 각각 `main`을 대상으로 PR을 열어. 먼저 병합된 PR이 다른 작업에 영향을 주면 남은 브랜치에 최신 `main`을 반영하고 해당 동작을 다시 확인해.

## 한국어로 리뷰하고 함께 배우기

직접 쓰는 **커밋 제목·본문과 PR 제목·본문은 한국어**로 작성해. 기존의 `feat:`, `fix:`, `docs:` 접두사와 명령어·파일명·API 이름은 원문을 써도 돼. 예를 들면 `fix: 공개 목록에서 초안 제외`처럼 동작이 드러나는 제목을 써.

PR 본문에는 **바꾼 이유, 먼저 볼 파일, 확인 방법과 실제 결과**를 적어. 확인이 남은 항목도 표시해. AI는 매 PR에서 이번 변경을 이해하는 데 도움이 되는 짧은 실습이나 리뷰 질문 하나를 제안해.

예를 들어 공개 필터 PR에서는 “글에서 `publish`를 생략하면 개발 서버와 공개 빌드에 각각 보일까?”를 먼저 예측해 봐. 같은 글로 두 결과를 확인하고 공개 여부를 결정한 코드 한 줄을 찾아보면, 다음 PR에서도 직접 그 규칙을 검토할 수 있어.

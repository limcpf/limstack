# 검토와 배포

limstack 저장소는 빌더 코드·레이아웃·CSS·의존성 잠금 파일을 버전별로 GitHub Releases에 제공해. 비공개 문서 저장소의 로컬 루트는 `~/documents`로 잡아. 여기서 `markdowns/`, `images/`, 발행 워크플로와 사용할 빌더 버전을 관리해. `.git/`과 `.github/`는 두 Syncthing 폴더 바깥에 위치해.

## 변경분 검토

1. 글과 이미지를 함께 커밋해서 문서 저장소의 `main`에 push해. 발행하고 싶을 때 문서 저장소에서 GitHub Actions를 수동 실행해. 워크플로는 시작 시점의 문서 커밋 SHA를 체크아웃하고, 그 커밋이 지정한 빌더 릴리스로 `publish: true`인 글을 빌드해. 생성한 `dist/`, 문서 커밋 SHA, 빌더 버전을 같은 빌드 ID로 추적할 수 있게 해.
2. Actions 실행 환경에서 이번 `dist/`를 로컬 HTTP로 열고, 마지막 성공 배포 이후 추가·수정된 공개 글의 실제 화면을 캡처해. 공개 글이 참조한 이미지 변경도 포함해. 글별 PNG와 검토용 HTML을 Telegram으로 보내. 삭제하거나 비공개로 전환한 글은 변경 요약에 표시하고, 공통 CSS나 레이아웃이 바뀌면 `Example`을 별도 검토 빌드로 렌더링해.
3. 홈(`/`), 전체 stack(`/stack/`), 변경의 영향을 받은 stack 목록은 메뉴부터 마지막 행까지 전체 페이지 PNG로 캡처해서 Telegram으로 보내. 한글 글꼴과 이미지가 준비된 뒤 캡처해. 긴 글은 첫 화면 PNG와 끝까지 읽을 수 있는 HTML을 함께 보내.
4. 건너뛴 파일은 GitHub Actions 실행 요약과 Telegram 검토 메시지 상단에 표시해. 보낼 글이 없어도 경고는 보내고, 이번 배포로 사라질 기존 공개 페이지가 있으면 표시해.

## 검토한 빌드 배포

Telegram 메시지에 빌드 ID와 GitHub 배포 워크플로 링크를 넣어. GitHub에서 검토한 빌드를 선택하면 캡처에 사용한 `dist/`를 그대로 공개 Cloudflare 사이트에 배포해. 배포가 실패하면 GitHub에서 같은 `dist/`로 재시도할 수 있게 해.

## 문서 한 편 검토

문서 저장소의 Actions에서 `문서 한 편 검토`를 수동 실행하고 `markdowns/java/servlet-request-flow.md` 같은 저장소 상대 경로를 입력해. 선택한 브랜치의 실행 시점 커밋에서 해당 글을 `build:doc`으로 렌더링해. 초안과 `Example`도 선택할 수 있어. 이미지·CSS·수식 폰트를 담은 독립 HTML을 개인 Telegram 대화로 보내면 검토가 끝나. Cloudflare 발행은 위의 전체 사이트 빌드와 승인 흐름을 사용해.

## 캡처 도구 선택

2차 구현에서는 실행 환경에 있는 호환 Chrome 또는 Chromium을 `puppeteer-core`로 여는 방식을 우선 검토해. 한 번 띄운 브라우저를 여러 페이지에 재사용하고 메뉴·목록에는 `fullPage: true`를 적용해. Mermaid 변환에 이미 호환 브라우저를 쓴다면 같은 설치본을 사용해. 이 선택으로 별도 브라우저 다운로드를 줄일 수 있어. 실제 빌드 시간과 메모리 사용량은 구현 단계에서 확인해. [Puppeteer 설치 방식](https://pptr.dev/guides/installation) · [캡처 옵션](https://pptr.dev/api/puppeteer.screenshotoptions)
